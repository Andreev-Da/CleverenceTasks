# О решении

Проекты находятся в папке Source.<br> 
Решение каждой задачи представлено в виде библиотеки классов + тестов.<br>
Т.к. не было требований к тестовым фреймворкам использовал TUnit.<br>

## Комментарии к задачам. 
#### Задача1.
Т.к. алгоритм кодирования по условиям задачи не меняется, я предпочел сосредоточиться на удобном API для вызова методов кодирования и декодирования.

#### Задача2.
Упавшие тесты для SimpleServer это норма, т.к. его алгоритм не является потокобезопасным.<br>
Интересный момент, в самой задаче клиенты подразделяются на пишущих и читающих. Даже сигнатуры методов GetCount и AddToCount говорят об этом!! И по сути может быть достаточным сделать AddToCount атомарным. Тут нужно побольше разобраться для чего мы это делаем и на сколько свежие данные нужны читателям. Ведь иначе можно вечно читать данные уйдя с TimeOutException.<br>
Самая тупа реализация представленная в AtomicServer, реализация полностью удовлетворяющая условиям задачи в ReaderWriterServer.

#### Задача3.
Философский вопрос, стоит ли нам продолжать парсинг если упал 1 лог. Ведь зачем отбраковывать всю партию. Но теоретически так можно уйти в вечный цикл

Тут правда нет комплексного теста, где проверялись бы все модули системы.<br>
А существующие тесты не успел дописать, т.к. во первых больше бы подошло фаззинг тестирование для парсеров, а во вторых анализ выходных данных требует чуть более индивидуального подхода, на что нет времени
